# HUNL_DATAGEN_FAILURE_MATRIX — every way a 10M-sample run can produce valid-looking but wrong data

Date: 2026-08-13. Read-only parallel audit task. Companion:
`HUNL_DATAGEN_SOURCE_AUDIT.md`, `HUNL_DATAGEN_ORACLE_PLAN.md`,
`HUNL_DATAGEN_FREEZE_CHECKLIST.md`.

Threat model: silent corruption — data that passes casual inspection
(finite, right shapes, plausible ranges) but is wrong. Loud crashes are
cheap; silence is the enemy. Most preventions below are already proven in
the project's Phase-2B pattern (`certification/phase2b/run_phase2b.py`,
line anchors cited; report `PHASE2B_PRODUCTION_DATASET.md`): atomic
renames, per-shard manifests with SHAs, fail-fast QA, audit resolves,
independent replay. The HUNL runner must reproduce each mechanism.

| # | Failure mode | How it silently corrupts | Preventive assertion / test (with existing pattern) |
|---|---|---|---|
| F-01 | **RNG drift / stream desync** — any reorder of board/range/pot draws, extra or missing draw (e.g. rejection-count coupling, SOURCE_AUDIT §3 line 2), or library RNG change | Every subsequent sample in the shard differs; distributions still look perfect | Draw-ledger reconciliation: per-batch expected pattern (4+G board + 2×(11,270 f32 + 376 u32) + 20 pot draws) counted by an instrumented THRandom wrapper over pilot batches (Phase-2A "RNG call accounting … verified over 3,000 batches"); byte-replay of shards from seed (run_phase2b.py:409-423, 39/39) makes any desync a loud SHA mismatch |
| F-02 | **Wrong player swap in targets** — P1/P2 blocks exchanged, or root-actor convention flipped (DeepHoldem permutes it; SOURCE_AUDIT §4 X8) | Targets are a valid solve of the MIRRORED state; all marginals look normal | Corpus items 43/44 (position-swap negative control, reflection identity at all-in u_1(S)=−u_2(S') via solver-free oracle A); dominated-range item 8 (sign of the dominant side must be +); assert root actor = seat0 = BB = block 1 against `hunl/config.py` `first_player` in the generator's config hash |
| F-03 | **Pot scaling error** — half-pot vs full-pot: normalizing by total pot (2×committed) or building `bets` from total pot | All targets off by exactly 2× (or pots doubled); still finite and well-shaped | Oracle A anchor: at all-in/check-down the exact value is known in CHIPS; a 2× factor fails the 1e−15 band instantly. Freeze the convention in code as `pot_half` (per-player committed) with the inversion audit recomputing `target_chips = target × pot_half` (run_phase2b.py audit-resolve pattern :320-333, 220/220) |
| F-04 | **Wrong blockers** — mask built from stale/wrong board, or range scatter using the wrong possible-hand index | Nonzero mass/targets on impossible hands, or silently truncated support | Per-sample BIT_EXACT checks: mask == recomputed `possible_hands_mask(board)` (G1.2 certified layer); ranges and targets exactly 0 outside mask (Phase-2B QA "range blocks … zero on impossible buckets"; corpus 15/39) |
| F-05 | **Target normalization by wrong pot** — e.g. dividing by the FEATURE (pot/stack) or by a stale previous sample's pot | Magnitudes plausible within a shard | Per-sample bound |target| ≤ stack/pot_half (Phase-2B "|target| ≤ 12.5" analogue, ORACLE_PLAN item 37); inversion audit re-derives pot from the serialized feature via the exact f32 cast chain and fresh-resolves (220/220 pattern); zero-sum residual band per sample (statistic, not correction — SOURCE_AUDIT §2.8) |
| F-06 | **Zero-support branch mishandling** — river killing a support renormalized by 0 or skipped inconsistently | NaN→0 flushes or biased CFVs on rare boards only | Corpus items 13/14 (zero-support rivers); global finiteness assert (Phase-2B "finite values everywhere"); the certified chance algebra never renormalizes reach (G1 transition gate, `hunl/chance.py` contract) |
| F-07 | **Nondeterministic BLAS (threads)** — threaded GEMM changes summation order | Bit-level drift; replay fails intermittently; targets differ across workers | Pin the certified stack (Phase-2B: bundled OpenBLAS `cd143947…`, BIT_EXACT_BACKEND, x86_64); corpus item 53 threads-1-vs-4 byte-identity; determinism SHA over 2 fresh processes (HUNL v1 pattern `c6c4eb4e…`) is a gate precondition |
| F-08 | **Shard seed collision** — two shards share a THRandom seed | Duplicated samples inflate effective dataset correlation | Derived seeds via SHA-256 of `"{tag}:{master}:shard:{idx:05d}"` (run_phase2b.py:97-99) + explicit all-unique assertion (Phase-2B: 110/110 unique) + cross-shard duplicate row check (F-11) |
| F-09 | **Stale engine SHA** — code edited after certification but manifest still claims the frozen SHA | Whole dataset generated by an uncertified engine | Every generating process verifies `git rev-parse HEAD` == pinned engine SHA `34a50560a30cbff156e979b59af6c00e39f7f1a9` AND clean `git status` before writing anything (Phase-2B "provenance pins … verified at start of every generating process"); manifest embeds engine/generator/config SHAs (run_phase2b.py:274-283) |
| F-10 | **Partial shard writes** — crash mid-file leaves a truncated but readable array | Short shard silently accepted | Write to `.tmp_shard_*` then `os.rename` (atomic on same fs) only after full write + SHA (run_phase2b.py:251,271-272); loader asserts exact row counts from the manifest; per-shard sample_count field |
| F-11 | **Duplicated samples** — resume bug, seed reuse, or copy-paste shard | Effective dataset smaller than claimed; training leakage between train/valid | SHA-256 over every serialized input row, global duplicate scan (run_phase2b.py:326-333; Phase-2B: 0 duplicates over 110,000 rows) — run across the train/valid boundary too |
| F-12 | **Float dtype drift** — f64 intermediates serialized as f64, or f32 truncation at a different point than certified | Files differ from the certified byte contract; replay on another host diverges | Schema asserts exact dtypes (HUNL_TURN_DATASET_V1: uint8/int32/float32); writer asserts `arr.dtype` before save; inversion audit reproduces the exact cast chain (Phase-2A D1 lesson: f64-vs-f32 chains collapse only if the contract is explicit) |
| F-13 | **Board-order dependent serialization** — same 4 cards stored in draw order vs sorted | Identical states hash differently; duplicate detection and caching break; suit-permutation audits fail | Canonical ascending card order asserted at write time (corpus item 26 BYTE_EXACT identity); the RNG draw order is preserved separately in the ledger (draw order ≠ storage order, documented) |
| F-14 | **Mask/ordering contract drift** — 1326-hand lex order or mask convention changes between generator and consumer | Ranges/targets permuted relative to training-time bucketing | Frozen ordering contract (`hunl/cards.py` "FROZEN — G1 ordering contract": lex (c0<c1) pairs); schema_version bump required for ANY layout change; golden-anchor pin (corpus 56) trips on silent permutation |
| F-15 | **THRandom state reuse across shards** — worker reuses a live generator object for the next shard | Shard k+1's stream depends on shard k's rejection count; replay from seed fails | One fresh THRandom per shard, constructed from the derived seed inside the shard function (Phase-2B: "each shard is one independent certified THRandom stream"); corpus item 49 |
| F-16 | **Resume-after-crash double generation** — restarted orchestrator regenerates a shard already on disk (or appends) | Mixed-provenance shard | On restart, existing shard files are SHA-verified against their manifest and SKIPPED only on match, else regenerated from scratch (run_phase2b.py:241-247 "existing files do not match manifest" assert); never append |
| F-17 | **Silent exception swallowing in workers** — try/except around the solve that substitutes zeros/last values | A fraction of targets are garbage with perfect shapes | NO retry/except-continue logic at all: every anomaly is fail-fast abort writing `FREEZE_DIVERGENCE.json` (run_phase2b.py:231; Phase-2B report: "0 failed, 0 retried, 0 dropped. No retry logic exists…"); worker exit codes checked by the orchestrator |
| F-18 | **Disk-full truncation** — write succeeds partially, rename still executed | Truncated arrays with valid headers | SHA computed from the RE-READ renamed file (run_phase2b.py:272) — truncation changes the SHA vs the in-memory content; free-space precheck; row-count assert on load |
| F-19 | **git-LFS / binary corruption on push** — pointer files instead of arrays, CRLF mangling, or partial LFS smudge | Repo copy differs from generated copy | Manifest SHAs are the source of truth: post-push CI/consumer re-hashes every file against the manifest before use (Phase-2B replay-verification pattern :420-422); `.gitattributes` pins binary handling; never rely on git object identity for data files |
| F-20 | **Wrong omitted-iteration window** — e.g. averaging over all 1000 iterations or off-by-one in the skip boundary | Systematic small bias in every target; distributions fine | Config hash includes (iters=1000, omit=500) (run_phase2b.py:79-96 pattern); golden-anchor pin (corpus 56) is sensitive to the averaging window (Phase-2A D2 elimination #5 showed ANY global window change destroys byte-exactness); pilot LP anchors (oracle C) bound the residual |
| F-21 | **Pot category/interval bug** — off-by-one in interval boundaries, or emitting the [100,200) gap / >19950 pots | Distribution subtly wrong; single-sample checks pass | Per-sample assert: pot ∈ {100} ∪ [200,400) ∪ [400,2000) ∪ [2000,6000) ∪ [6000,19950] exactly as frozen (negative corpus items 28/32); cross-shard pot histogram vs analytic law (Phase-2B pot-distribution QA pattern: min/max/mean vs expected) |
| F-22 | **Batch board leakage** — board changes mid-batch or set_board not refreshed (stale strengths/sort order from previous board) | Ranges sorted by the WRONG board's strengths — statistically near-invisible | Phase-2B QA "board constant within each generation batch of 10"; per-batch assert that the strength ordering used for the range scatter was computed from the batch board (recompute-and-compare on audited rows via inversion, 220/220 pattern) |
| F-23 | **Manifest claims vs actual config** — generator run with a locally edited config while the manifest records defaults | Irreproducible dataset that looks pinned | Config hash = SHA-256 of the canonical JSON of the LIVE config object (run_phase2b.py:92-96), recorded per shard; replay (F-01) fails if the live config differed |

Cross-cutting rule (Phase-2B requirement inherited): **no retry logic
anywhere in the runner** — a retried stochastic step invisibly forks the
RNG stream (F-01) and masks real bugs (F-17). The only loop allowed is the
board rejection sampler, which is part of the certified stream itself
(PHASE2B_PRODUCTION_DATASET.md "Failed / retried samples").
