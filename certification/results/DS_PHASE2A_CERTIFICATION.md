## Divergence reports (freeze-first protocol)

### D1 — EXPLAINED (tooling insight, no engine impact): tree bets f64 vs Lua per-node f32
- Frozen input: valid row 1 (board 3=Kh, pot 106.26386404037476).
- Finding: golden `tree.py` carries float64 bets across levels; Lua stores
  f32 per node (`arguments.Tensor{}`), children derive from truncated values.
  20 tree nodes differ for this pot (e.g. 318.79158783 vs f32-chained
  318.79159546).
- Impact measured: **zero** — the lookahead's own f32 pot store collapses
  both chains to identical values (resolve outputs byte-identical under both
  builders on the frozen row). Kept anyway for literal fidelity:
  `datagen/lua_tree.py` `LuaF32TreeBuilder` (dependency-injected; golden
  untouched). Candidate future golden fidelity note, currently value-inert.

### D2 — target divergence on 134/200 bundled rows — EXPLAINED-BY-ELIMINATION (author-side provenance), not conclusively proven
- First divergence frozen: valid row 1, target idx 20 (P1, card Ks):
  ours `5.6546307` (0x40B4F32C) vs stored `5.6546264` (0x40B4F323), 9 ULP;
  full input state recorded in the census log.
- Census over all 200 rows: 66 byte-exact; 134 diverging with ≤10/72
  entries, max abs 5.0e-3, median ~1e-6, max 364,381 ULP on tiny entries;
  divergence correlates with board (Kh 46 rows … Ks 2 rows) and spans the
  whole pot range.
- Hypotheses tested and ELIMINATED, each by direct experiment on frozen rows:
  1. tree f64 chain (D1) — byte-identical outputs both builders;
  2. missing/present 999999 regret cap — cap-free run byte-identical
     (cap provably never binds on these inputs either);
  3. FTZ/DAZ denormal flushing — MXCSR-forced FTZ+DAZ run byte-identical;
  4. GPU generation — impossible per-row (exact and diverging rows share
     batches); 66 exact rows also rule it out;
  5. different cfr_iters/skip/averaging window or ±1 iteration — any global
     config change would leave ~0 rows byte-exact; 66/200 exact excludes it;
  6. target post-processing (zero-sum correction) — stored and recomputed
     targets show same-order zero-sum residuals, no correction signature.
- Remaining explanation (supported, not proven): the bundled TrainSamples
  were generated by a **pre-release version of the author's solver** whose
  behavior differs conditionally (state-dependently) from the released Lua.
  Supporting evidence: (a) our engine is byte-identical to the RELEASED Lua
  on ~25k fresh trace tensors including 1000-iteration street-2 endpoint
  resolves; (b) 66/200 rows reproduce byte-exactly — a per-row conditional,
  impossible under any global config/code difference on our side;
  (c) the sibling artifact `final_cpu.info` provably predates the released
  training code (missing `gpu` field, epoch 9849 vs shipped defaults);
  (d) upstream git history is a single initial commit — samples were
  imported, not generated by the released code in-repo.
- Conclusive proof would require running the released Lua datagen on the 200
  reconstructed inputs under Torch7 — no Torch7 runtime exists here
  (building LuaJIT+torch7+nn in 2026 is high-risk); recorded as an oracle
  limitation alongside M3/RNG.
- **Per instruction, bulk generation and training are NOT started** while
  this divergence lacks conclusive proof; owner decision requested (see
  verdict).

## Verdict on generator safety for final-dataset production

The generator itself is certified: RNG bit-exact vs author C source, seeded
byte-reproducibility across processes, serialization byte-exact, sampling
distributions correct, and the deterministic target path runs exclusively
through the Golden Baseline engine (which is byte-identical to the released
Lua reference on the full trace corpus). The 66/200-vs-134/200 split is
evidence about the **bundled samples' provenance**, not about our generator:
against the only engine standard we have committed to (released Lua =
Golden Baseline), the generator is faithful.

**Formally, per the run's own rule ("no bulk generation while an unexplained
divergence exists"), D2 is explained-by-elimination but not proven — the
owner must decide:**
- **Option A (recommended):** accept D2 as an author-side provenance
  artifact; declare the bundled TrainSamples a mixed oracle (structure
  BIT_EXACT, targets NUMERIC ≤5e-3); proceed to bulk generation with the
  certified generator (all new data self-consistent with the certified
  engine — arguably *more* consistent than the author's own mixed-era data).
- **Option B:** attempt a Torch7 runtime build to run released-Lua datagen
  on the 200 reconstructed inputs first (time-boxed; success not
  guaranteed); upgrade D2 to proven before production.
